# 舞台走位校验系统

一款舞台走位（Blocking）校验 Web 应用：在「舞台区域连接图」上标注各区域间的通行耗时与**通道封闭时段**，为演员按时间下达「到位口令」（可含**停留要求**），系统以**连续口令延误传导**模式逐段推演——首条口令视为准时到位，之后每段从「max(计划时刻, 上段实际到达) + 停留时长」出发，**逐边推演**实际行进过程——进入连接若与封闭时段重叠，会在区域**原地等待**或**自动改走其他路径**，据此计算**实际到达时刻**；某段的迟到会**传导**给后续区段，后续间隔充足时可**吸收延误**、恢复准时。结果区逐段展示计划/实际出发、实际到达、继承延误与最终迟到，标出**迟到**与**不可达**区段，支持编辑后即时重算与一键导出 Markdown 校验报告。

技术栈：Node.js + Express + 原生 HTML/CSS/JavaScript（无任何前端构建步骤）。

## 一键启动（Docker Compose）

```bash
docker compose up --build
```

启动后访问：**http://localhost:3000**（容器内服务端口 `3000`，Compose 默认映射到主机 `3000` 端口）

> 首次启动时，若数据文件不存在，系统会自动写入内置示例数据（9 个舞台区域、11 条连接——其中 2 条带封闭时段、3 位演员、12 条口令，含刻意设计的「等待」「绕行」「停留」「迟到传导与吸收」与「不可达」演示区段）。

## 配置项

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `PORT` | `3000` | Web 服务监听端口（Compose 中映射为主机 3000 端口） |
| `DATA_DIR` | `./data`（容器内 `/app/data`） | 数据文件 `data.json` 存放目录 |

Compose 默认将数据目录挂载为命名卷 `stage-data` 以持久化修改；执行 `docker compose down -v` 删除卷后重启即可恢复示例数据（也可在页面右上角点击「恢复示例数据」）。

## 本地开发（不用 Docker）

```bash
npm install
npm start
# 访问 http://localhost:3000
```

要求 Node.js ≥ 18。

## 功能说明

- **舞台区域**：维护区域名称与备注（如 舞台中央、侧台右、后台化妆间）。
- **区域连接**：维护无向连接、通行耗时（秒）与**通道封闭时段**（可添加多段起止秒数区间），同一对区域仅允许一条连接。
- **演员**：维护演员姓名与角色。
- **到位口令**：按「演员 + 目标区域 + 时间」下达口令，时间支持 `90`（秒）或 `01:30`（分:秒）两种输入格式；每条口令可设 **0～600 秒停留要求**（到位后须停留的秒数，缺省 0），停留会推迟前往下一条口令的出发时刻。
- **校验结果（连续口令延误传导）**：对每位演员，将其口令按时间升序排列后**连续推演**（详见下节规则）：
  - ✅ **准时**：实际到达时刻 ≤ 下一口令时刻，显示余量秒数、实际到达时刻与实际路线；若继承了上段延误且被本段吸收，会标注「延误已吸收」；
  - ❌ **迟到**：实际到达时刻 > 下一口令时刻，红色高亮并显示「最终迟到 X 秒」，该迟到会**传导**给后续区段；
  - ⛔ **不可达**：两区域在连接图上不连通（封闭时段只会造成等待或绕行，不会造成不可达）；不可达区段无法推演到达时刻，其后一区段从计划时刻重新起算。
- **传导明细**：结果区逐段展示**计划出发 / 实际出发 / 实际到达 / 继承延误 / 最终迟到**，并以 🔁 徽标标出继承延误、以 ✔ 徽标标出延误吸收。
- **等待展示**：结果区在路线下方逐边列出出发 / 到达时刻，并以 ⏱ 徽标标出**等待位置（区域）与时长**。
- **即时重算**：任何新增 / 编辑 / 删除操作（含封闭时段与停留编辑）保存后立即重新校验并刷新结果。
- **导出报告**：点击「导出校验报告」下载 Markdown 格式报告（含汇总表、每位演员的区段明细、**延误传导明细**与**逐边动态路线明细**）。
- **级联一致性**：删除区域会同时删除相关连接与口令；删除演员会同时删除其全部口令。

## 连续口令延误传导规则

- 每条口令可维护 **0～600 秒**的停留要求（整数秒）；旧数据文件中没有停留字段的口令按 **0** 处理，完全兼容。
- 对每位演员按口令时间升序**连续推演**：**首条口令视为准时到位**（实际到达 = 计划时刻）。
- 从某条口令前往下一条时：**实际出发时刻 = max(该条计划时刻, 该条实际到达时刻) + 该条停留时长**，再复用封闭等待 / 绕行算法（时间依赖 Dijkstra）推演下一条口令的**实际到达时刻**。
- **继承延误** = max(0, 上一条口令实际到达 − 该条计划时刻），会逐段传导；**最终迟到** = max(0, 实际到达 − 下一口令时刻）。
- 后续区段间隔充足时，延误会被**吸收**（实际出发被计划时刻"接住"），演员恢复准时。
- 不可达区段没有实际到达时刻，传导中断：下一区段从其计划时刻重新起算（结果区与报告中会注明）。

## 通道封闭时段规则

- 每条连接可维护 **0 至多段**封闭时段，每段为起止秒数区间 `[开始, 结束)`（**含开始、不含结束**），开始必须严格小于结束，均为不小于 0 的整数秒。
- 演员在时刻 `t` 进入一条通行耗时为 `w` 的连接时，占用区间为 `[t, t+w]`；若该区间与任一段封闭区间**重叠**（`t < 结束` 且 `t+w > 开始`），则此时刻不可进入。
- 冲突时演员在该连接**起点所在的区域内等待**，直至封闭结束（最早可进入时刻 = 封闭结束时刻；多段封闭会依次向后滚动计算）。
- 校验算法会比较「等待」与「绕行其他路径」两种方案，取**最早到达时刻**的路线作为实际路线；等待位置与时长会在结果区和报告中展示。
- 封闭时段为有限区间，因此只会推迟到达、不会影响图连通性；「不可达」仍仅表示区域间没有任何连接路径。
- 旧数据文件中没有封闭时段字段的连接按「无封闭」处理，完全兼容。

## API 概览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/data` | 获取全部数据（区域 / 连接 / 演员 / 口令） |
| GET | `/api/validate` | 执行走位校验（连续延误传导），返回区段级结果（含计划/实际出发、实际到达、继承延误、最终迟到、逐边路线与等待明细） |
| GET | `/api/report` | 下载 Markdown 校验报告 |
| POST | `/api/reset` | 恢复内置示例数据 |
| POST / PUT / DELETE | `/api/areas`、`/api/edges`、`/api/actors`、`/api/cues`（`/:id`） | 四类资源的增改删 |

`edges` 的创建 / 更新请求体示例：

```json
{
  "a": "area-wing-r",
  "b": "area-center",
  "seconds": 4,
  "closures": [ { "start": 10, "end": 14 }, { "start": 30, "end": 36 } ]
}
```

`closures` 可省略（等价于无封闭）；每段需满足 `0 ≤ start < end` 且为整数秒，否则返回 400。

`cues` 的创建 / 更新请求体示例：

```json
{
  "actorId": "actor-zhang",
  "areaId": "area-center",
  "time": 90,
  "stay": 15,
  "note": "上台亮相"
}
```

`stay`（停留秒数）可省略，默认 `0`；需为 `0～600` 的整数秒，否则返回 400。

## 项目结构

```
├── server.js            # Express 入口
├── src/
│   ├── store.js         # JSON 文件持久化 + 示例数据初始化
│   ├── graph.js         # 时间依赖推演：封闭时段等待 / 绕行 + 最早到达（Dijkstra）
│   ├── validate.js      # 走位校验核心：连续口令延误传导（停留 + 继承延误 + 吸收）
│   ├── report.js        # Markdown 报告生成（含传导明细与动态路线明细）
│   └── routes.js        # REST API 路由与入参校验
├── public/              # 前端（原生 HTML/CSS/JS）
├── seed/sample-data.json# 内置示例数据（含封闭时段演示）
├── Dockerfile
└── docker-compose.yml
```
